# ADR 001 — Architecture cible du projet NFT Market Collector

**Statut** : accepté — 07/11/2026
**Auteur / owner** : Yann Monkam Nono

## Contexte

L'application doit répondre chaque jour à une question d'analyste : évolution des prix et du volume de
4 collections NFT Solana, et concentration de la demande sur quelques acteurs. La source principale
(API Magic Eden) est publique, paginée (plafond observé : 30 pages de 500 activités par run), limitée à
120 requêtes/min et susceptible de changer de schéma. Le projet est maintenu par une seule personne, sur
un poste personnel, sans budget d'infrastructure.

**Constat du profilage du premier run réel (07/11/2026)** : 60 000 activités, dont 0,1 % de ventes (52),
34 % d'offres, 38 % de mises à jour de pools et 27,6 % d'annonces ; un run couvre seulement 12 à 42 h
selon la collection. Une architecture « une grosse collecte de 30 jours » est donc impossible avec cette
source ; l'historique doit être **accumulé**.

## Exigences mesurables

| Exigence | Valeur cible | Pourquoi |
|---|---|---|
| Fraîcheur | données de J-1 disponibles chaque matin ; alerte si dernière observation > 72 h | décision quotidienne, pas en temps réel |
| Complétude | pas de trou entre deux runs ; tout trou est daté (R10) | l'historique est construit par accumulation |
| Volume | ~50 ventes et ~20 000 offres/jour mesurées sur 4 collections ; < 10 M lignes/an | profilage du 07/11/2026 |
| Durée d'exécution | < 5 min par run | dominée par la limite de débit de l'API |
| Disponibilité | un run manqué est rattrapable (rejeu, fenêtre de 30 j) | pas de SLA externe |
| Rétention | raw 90 j, curated 13 mois | rejeu possible, historique annuel |
| Utilisateurs | 1 à 5 analystes, lecture seule | usage personnel / petite équipe |
| Sensibilité | wallets = identifiants indirects → pseudonymisation | RGPD (minimisation) |

## Options comparées

| Option | Description | Bénéfices | Coûts / risques |
|---|---|---|---|
| **1. Simple** | Script unique, résultat dans un CSV écrasé à chaque run | Très rapide à écrire | Pas de raw pour rejouer, pas d'historique, doublons possibles, pas de contraintes |
| **2. Proportionnée (retenue)** | Batch Python quotidien en étapes (collect → validate → transform → publish), raw JSON horodaté, SQLite avec contraintes et UPSERT, vues de mart, rapport d'exécution | Rejouable, idempotent, contrôlé, zéro infrastructure, exécutable par un tiers en 5 min | Un seul écrivain à la fois ; pas de planificateur intégré ; mono-machine |
| **3. Évolutive** | Ingestion streaming (WebSocket/webhooks → Kafka), lake objet (S3 + Parquet), warehouse (PostgreSQL/BigQuery), orchestration Airflow | Latence en secondes, montée en charge, multi-équipes | Plusieurs services à exploiter, coût, complexité sans exigence qui la justifie |

### Sous-décisions

- **Collecte incrémentale par filigrane** plutôt que pagination complète à chaque run : on pagine du plus
  récent au plus ancien et on s'arrête au dernier `blockTime` déjà chargé (moins 1 h de recouvrement,
  absorbé par l'idempotence). Le filigrane n'avance qu'après une publication réussie (reprise sûre).
  Option écartée : WebSocket / flux temps réel (pas d'exigence de latence, service à superviser en continu).
- **Ventes + offres** : les ventes seules (52 en un jour) ne suffisent pas à décrire le comportement des
  acheteurs ; les offres (20 000/jour) mesurent la profondeur et la concentration de la demande, sans
  nouvelle source ni nouvel appel (même flux d'activités).
- **SQL plutôt que NoSQL (MongoDB)** : les requêtes sont des agrégations relationnelles (par collection ×
  jour, par acheteur) et la donnée curated a un schéma stable et contrôlé. Le besoin de souplesse de
  schéma est couvert par la zone raw JSON. MongoDB aurait été pertinent si l'on stockait les métadonnées
  hétérogènes des NFT (attributs, traits) — hors périmètre.
- **SQLite plutôt que PostgreSQL** : un seul écrivain (le batch), peu d'utilisateurs, < 1 M lignes/an ;
  SQLite offre contraintes, transactions, index et vues sans serveur. Mode WAL pour lire pendant l'écriture.
- **Batch plutôt que streaming** : aucune décision ne se prend en moins de quelques heures ; l'API est
  interrogeable a posteriori (historique de 30 j) ; le rejeu par fichier est simple.
- **Lake / Warehouse / Mart** : on garde une **zone raw** (rôle de lake : rejeu après bug ou changement de
  règle), une **base curated** (rôle de warehouse léger : `fact_sale` + `dim_collection`) et des **vues
  mart** pour l'usage. Pas de Data Lake objet ni de Warehouse séparé : une seule source métier, volume faible.

## Décision

Option 2 : pipeline batch Python quotidien **incrémental** (filigrane par collection), zone raw JSON
horodatée, base SQLite curated contrainte et idempotente (`fact_sale`, `fact_bid`), marts sous forme de
vues SQL + exports CSV et rapport HTML.

## Arguments

- Chaque composant répond à une exigence : raw → rejeu et preuve ; règles R0-R9 → qualité ; clé primaire +
  UPSERT → absence de doublons au rejeu ; `run_log` + `run_report.json` → observabilité ; pseudonymisation
  → minimisation RGPD.
- Plus simple option qui satisfait les exigences et que l'auteur peut exploiter seul.

## Conséquences positives

- Exécution complète en local en quelques minutes, sans compte cloud ni service à installer.
- Reproductible par un tiers à partir du README ; tests automatisés.
- Incidents détectés et tracés sans corrompre la base (transaction tout-ou-rien).

## Conséquences négatives

- Pas de planification intégrée : le run quotidien dépend d'un cron / planificateur de tâches externe.
- SQLite limite les écritures concurrentes et l'accès réseau multi-utilisateurs.
- Dépendance à une seule marketplace : les volumes ne représentent pas tout le marché Solana.
- L'historique ne commence qu'au premier run : les tendances de prix restent fragiles tant que la base
  ne couvre que quelques jours.

## Condition de réexamen

Revoir cette décision si l'une des conditions suivantes apparaît :
- besoin d'alerte en moins de 5 minutes (ex. détection de chute de floor) → ingestion événementielle ;
- R10 signale des trous de façon répétée (collection trop active pour 30 pages/jour) → runs toutes les
  6 h, ou clé API Magic Eden pour un débit plus élevé ;
- plus de 10 collections ou plus de 5 M lignes, ou durée de run > 15 min → Parquet partitionné par date
  et/ou PostgreSQL ;
- plusieurs utilisateurs écrivant ou consultant à distance → PostgreSQL + API de lecture ;
- ajout d'une seconde marketplace (Tensor) → couche d'intégration (warehouse) avec définitions communes.
